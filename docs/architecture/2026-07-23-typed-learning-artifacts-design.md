# Typed Learning Artifacts

**Status:** Approved design, pending written review  
**Date:** 2026-07-23

## Purpose

ChalkPilot should use the room display for concise visual context and active
learning moves, not as a transcript or document dump. The learner continues to
respond naturally through speech and writing on the board. The canvas reacts to
that evidence by creating, updating, revealing, or focusing one relevant
artifact.

This release adds a small set of trusted, typed artifacts. AI-generated HTML,
JavaScript, React, and SVG are deferred until a separate sandbox can isolate
them safely.

## Design Principles

1. **Learning action before media format.** The worker chooses an artifact
   because it helps the learner compare, predict, retrieve, apply, explain, or
   inspect a process.
2. **Board-first interaction.** The display presents the task or context; the
   learner answers through the board or voice. Laptop clicks are not required.
3. **One focal artifact.** Each job creates or updates one principal section
   and focuses it. Supporting sections are exceptional.
4. **Progressive disclosure.** Answers, hints, and later worked-example steps
   stay hidden until they are pedagogically useful.
5. **Update before append.** The worker reuses a stable section ID when the
   concept or task is already present.
6. **Validated data only.** Model output crosses a Zod schema before persistence
   or rendering. Renderers never evaluate model-authored code.
7. **Lean runtime.** Trusted React and native SVG cover the first release
   without a general code sandbox or heavyweight visualization runtime.

These principles are mechanisms, not claims about fixed learning styles.
Visuals are used only when the representation suits the concept.

## Supported Artifact Catalog

### Existing presentation artifacts

- `markdown`: short explanations, compact tables, code snippets, and source
  notes. It is a fallback, not the default response format.
- `math`: one focal display equation or derivation fragment.
- `mermaid`: trusted rendering of model-authored Mermaid for flowcharts,
  relationships, state diagrams, and concept maps.
- `image`: an approved HTTP(S) image URL with alt text from the section title.
- `youtube`: a validated YouTube or YouTube No-Cookie URL.

### New `chart`

Purpose: make quantities, trends, distributions, and relationships visible.

The typed payload contains:

- a variant: `line`, `bar`, or `scatter`;
- an optional x-axis and y-axis label;
- one to four named series with one to 100 points each;
- string or numeric x-values and finite numeric y-values;
- zero to eight annotations containing a label, an existing x-value, and an
  optional finite y-value.

A trusted React/SVG renderer computes scales and geometry. The payload contains
no formulas, CSS, SVG markup, callbacks, or expressions. Function plots are
represented by sampled points generated by the worker.

### New `comparison`

Purpose: contrast concepts, methods, examples, misconceptions, or trade-offs
without forcing the learner to parse prose.

The payload contains two to four columns. Each column has a heading, a concise
summary, zero to five points, and an optional semantic emphasis token:
`neutral`, `positive`, or `caution`. Arbitrary colors and HTML are not allowed.

### New `sequence`

Purpose: show a process, proof, derivation, worked example, or causal chain with
controlled scaffolding.

The payload contains two to eight ordered steps, a stable ID and title for each
step, concise Markdown content, an active step ID, and a reveal policy. The
renderer can show only the active step, all steps up to the active step, or the
complete sequence. The worker advances the state after evidence from the board
or conversation.

### New `checkpoint`

Purpose: elicit prediction, retrieval, classification, explanation, or transfer
before presenting the answer.

The payload contains:

- a mode: `prediction`, `retrieval`, `classification`, or `transfer`;
- the prompt and either no choices or two to six concise choices;
- an optional hint;
- an optional expected answer and feedback;
- a status: `unanswered`, `attempted`, `correct`, or `revise`;
- explicit booleans controlling whether the hint, answer, and feedback are
  visible.

The display does not require an answer form. The learner responds by voice or on
the board, and the worker updates the artifact after interpreting that evidence.

## Artifact Selection Policy

The canvas worker should:

- use `checkpoint` when an independent attempt or retrieval opportunity is more
  useful than another explanation;
- use `sequence` for a worked example, multi-step process, or progressively
  revealed derivation;
- use `comparison` when distinctions or misconceptions are central;
- use `chart` when values, change, or a quantitative relationship matter;
- use `mermaid` for topology, dependencies, flows, and conceptual structure;
- use `math` for one focal symbolic relationship;
- use media only when a valid, relevant URL already exists;
- use Markdown only when a concise textual representation is genuinely best.

The worker should not create a visualization merely for decoration. It should
prefer the simplest artifact that supports the next learner action.

## State and Persistence

`CanvasSectionInput` remains a discriminated union. Textual and media kinds keep
their current string `content`. Structured kinds carry a typed `data` object.

Existing textual sections remain stored as `<section-id>.md`. Structured
sections are stored as `<section-id>.json`; the section kind determines the
format. Canvas metadata continues to live in `canvas/state.json`, so current
sessions remain readable without migration.

The display protocol already transfers the complete validated canvas state.
Structured payloads therefore travel through the same snapshot and update
messages as existing sections.

## Rendering Boundary

A small renderer registry maps each section kind to one trusted React
component. Every component receives an already validated section.

- Chart geometry is generated by application code as SVG.
- Comparison uses semantic HTML and a responsive CSS grid.
- Sequence and checkpoint use semantic state styling and progressive
  disclosure.
- The new structured renderers do not use `dangerouslySetInnerHTML`, `eval`,
  dynamic imports, or model-authored styles.

The existing Mermaid renderer remains the one exception: it injects only SVG
returned by Mermaid configured with `securityLevel: "strict"`. Raw model-authored
SVG is never accepted.

Unknown or invalid persisted sections fail validation and produce a clear
session error. They are not silently downgraded to Markdown.

## Agent and Interaction Flow

1. The voice agent delegates a semantic learning goal such as comparison,
   diagram, exercise, explanation, or formula.
2. The canvas worker reads the latest canvas and corrected board image.
3. The worker selects the simplest suitable artifact and calls the existing
   typed upsert action.
4. The repository validates and persists the complete section.
5. The canvas update is broadcast to both the control view and clean display.
6. The worker focuses the relevant section and privately reports completion to
   the voice agent.
7. Later evidence causes an update to the same section, such as revealing the
   next step or marking a checkpoint `revise`.

This release does not add autonomous periodic camera uploads. Camera-triggered
session orchestration is a separate design decision.

## Explicit Exclusions

The first release does not support:

- raw HTML, JavaScript, React, CSS, or SVG;
- generated code execution;
- arbitrary iframes or external embeds;
- sandboxed mini-apps;
- autoplaying media;
- direct external network requests from artifacts;
- model-selected fonts, colors, animations, or layout code;
- large multi-panel dashboards;
- interaction that requires the room display to be touch-enabled;
- decorative visualizations with no learning purpose;
- invented or unverified media URLs.

YouTube remains the only iframe-based artifact and uses the existing validated
host allowlist.

## Error Handling

- Schema violations fail the canvas job with a concise visible error.
- A renderer error is isolated to its section and does not replace the canvas.
- Invalid chart ranges or empty data fail validation instead of rendering a
  misleading graph.
- A worker must not claim an artifact was created unless persistence succeeds.
- Existing content stays visible when an update fails.

## Verification

The implementation must cover:

- schema acceptance and rejection for every new kind;
- structured JSON persistence and legacy Markdown compatibility;
- append and update behavior for each new kind;
- accessible rendering of charts, comparisons, sequences, and checkpoints;
- progressive-disclosure states;
- display-channel serialization;
- worker tool calls for each new kind;
- a browser flow showing a live worker-created visual artifact in the session
  canvas and clean display;
- the existing Node 24 check and Playwright suites.

## Deferred Sandbox

A future `sandboxed_app` artifact may execute generated code only inside a
separately designed iframe sandbox with no same-origin privilege, network,
storage, navigation, popups, forms, downloads, camera, or microphone. It will
use a bounded validated message protocol and resource limits.

That sandbox is deliberately not represented in the first-release schema. It
must be designed, threat-modeled, and approved separately.
